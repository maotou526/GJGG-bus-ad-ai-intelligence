# 全局消息提醒系统设计方案 v1.0

> 目标：设计一套“全局通用”的消息通知机制，适用于预订、上刊/下刊、AI审核、调线审核、告警、系统广播等所有业务场景。
>
> 说明：本方案以 **2 张核心表**为主（`bs_notice`、`bs_notice_user`），消息模板暂不落库，先用**静态模板常量**实现。

---

## 1 系统概述

### 1.1 功能目标

- 建立全局通用的消息提醒系统，支持任意业务场景的消息推送、广播通知、待办提醒等功能。

### 1.2 核心特性

- 支持一对一、一对多、全局广播
- 支持关联任意业务对象（通过 `rec_table` + `rec_id`）
- 支持已读/未读状态管理、删除（用户侧软删除）
- 支持待办处理状态（处理/忽略）
- 支持优先级与过期机制
- 支持 WebSocket 实时推送（可选）

### 1.3 设计理念

- **消息内容与用户接收记录分离**
  - 消息内容存放在 `bs_notice`
  - 每个用户的已读/删除/处理状态存放在 `bs_notice_user`
- **广播消息只存一份内容**
  - 广播/多播由 `bs_notice_user` 为不同用户生成接收记录来实现
- **与业务解耦**
  - 用 `rec_table`（业务标识）+ `rec_id`（业务记录主键ID）关联任意业务对象

## 2 数据表设计（继承 BaseDataModel）

> 本仓库业务表通常继承 `BaseDataModel`（包含 `CoreModel` 字段与业务通用字段）。
> 本文仅列出“业务特定字段”，通用字段（如 `id/create_datetime/update_datetime/enabled_mark/agent_id/...`）默认均存在。

### 2.1 系统消息主表（NoticeModel）

**数据库表名**：`bs_notice`

| 字段名称 | 字段代码 | 类型 | 必填 | 说明/备注 |
|---|---|---:|:---:|---|
| 消息类型 | `msg_type` | Int | Y | 1系统通知 2业务消息 3告警消息 4待办提醒 |
| 关联业务表 | `rec_table` | Char(50) | N | 业务标识，如 `booking_order`、`on_air_order`、`vehicle_transfer` |
| 关联业务ID | `rec_id` | Char(36) | N | 业务记录主键ID（UUID字符串） |
| 消息标题 | `title` | Char(200) | Y | 标题 |
| 消息内容 | `content` | Text | N | 支持富文本/Markdown |
| 跳转链接 | `jump_url` | Char(500) | N | 点击跳转的前端路由/URL（建议为前端路由） |
| 优先级 | `priority` | Int | Y | 1紧急 2普通 3低（默认2） |
| 发送方式 | `send_type` | Int | Y | 1指定用户 2指定角色 3指定部门 4全局广播 5混合模式 |
| 发送人ID | `sender_id` | Char(36) | N | 系统消息可为空或填 `"system"` |
| 发送人姓名 | `sender_name` | Char(100) | N | 冗余字段 |
| 发送时间 | `send_time` | DateTime | Y | 建议 `auto_now_add` |
| 过期时间 | `expire_time` | DateTime | N | 过期后前端查询应过滤 |
| 扩展数据 | `extra_data` | JSON | N | 存储发送范围/附加信息（见下文约定） |

#### 2.1.1 `send_type` 与 `extra_data` 约定

`send_type` 的作用：**定义接收人范围如何解析**，从而生成 `bs_notice_user` 接收记录。

推荐做法：`extra_data` **不要塞大量用户ID**，尽量仅存角色/部门ID，发送时动态查询用户并批量落接收记录。

- `send_type=1`（指定用户）：

```json
{"user_ids": ["u1", "u2"]}
```

- `send_type=2`（指定角色，支持多个角色）：

```json
{"role_ids": ["r1", "r2"]}
```

- `send_type=3`（指定部门，支持多个部门）：

```json
{"dept_ids": ["d1", "d2"]}
```

- `send_type=4`（全局广播）：

```json
{}
```

- `send_type=5`（混合模式：角色 + 部门 + 用户）：

```json
{
  "role_ids": ["r1", "r2"],
  "dept_ids": ["d1"],
  "user_ids": ["u1"]
}
```

> 说明：`send_type=2/3/5` 时，`extra_data` 的规模通常很小（仅若干 role/dept/user 的ID），不会很大。

#### 2.1.2 业务约束与索引建议

- `rec_table + rec_id` 用于业务追溯（允许为空表示纯系统广播或无业务对象）
- 过期消息保留在库中，但查询时过滤：`expire_time IS NULL OR expire_time > NOW()`
- 索引建议：
  - `msg_type`
  - `(rec_table, rec_id)`
  - `send_time`
  - `expire_time`

---

### 2.2 用户消息关联表（NoticeUserModel）

**数据库表名**：`bs_notice_user`

| 字段名称 | 字段代码 | 类型 | 必填 | 说明/备注 |
|---|---|---:|:---:|---|
| 消息ID | `notice_id` | Char(36) | Y | 关联 `bs_notice.id` |
| 接收人用户ID | `user_id` | Char(36) | Y | 接收消息的用户ID |
| 接收人姓名 | `user_name` | Char(100) | N | 冗余字段 |
| 阅读状态 | `read_status` | Int | Y | 0未读 1已读（默认0） |
| 阅读时间 | `read_time` | DateTime | N | 用户阅读时间 |
| 处理状态 | `handle_status` | Int | Y | 0未处理 1已处理 2已忽略（默认0） |
| 处理时间 | `handle_time` | DateTime | N | 用户处理时间 |
| 是否删除 | `is_deleted` | Boolean | Y | 用户侧删除（默认 False） |

#### 2.2.1 业务约束

- 一条消息（`notice_id`）可对应多条用户记录（实现广播/多播）
- 用户删除消息：只更新 `is_deleted=True`，不物理删除
- `handle_status` 主要用于 `msg_type=4`（待办提醒），其他类型可保持默认 0
- 组合唯一：`(notice_id, user_id)` UNIQUE

#### 2.2.2 索引建议

- `notice_id`
- `(user_id, read_status, is_deleted)`：未读数/未读列表
- `(user_id, handle_status, is_deleted)`：待办列表
- `(user_id, is_deleted)`：有效消息列表

#### 2.2.3 状态流转

```
read_status: 0未读 → 1已读（用户打开消息/详情）
handle_status: 0未处理 → 1已处理（完成待办）
handle_status: 0未处理 → 2已忽略（忽略待办）
```

## 3 业务逻辑设计

### 3.1 消息发送流程

```
[业务触发点]
    ↓
[解析接收人范围]（根据 send_type + extra_data）
    ↓
[创建消息主记录] bs_notice（1条）
    ↓
[批量创建接收记录] bs_notice_user（N条，按用户维度）
    ↓
[WebSocket 推送]（可选）
```

#### 3.1.1 接收人解析规则（建议）

- `send_type=1`：直接使用 `extra_data.user_ids`
- `send_type=2`：按 `extra_data.role_ids` 查询角色下用户
- `send_type=3`：按 `extra_data.dept_ids` 查询部门下用户
- `send_type=4`：查询全量活跃用户（如 `is_active=True`）
- `send_type=5`：角色用户 + 部门用户 + 指定用户合并去重

> 备注：接收人解析完成后，建议做去重与过滤（禁用用户/离职用户/无权限用户）。

### 3.2 消息查询逻辑（SQL 示例）

#### 3.2.1 查询未读数量

```sql
SELECT COUNT(*)
FROM bs_notice_user
WHERE user_id = '当前用户ID'
  AND read_status = 0
  AND is_deleted = 0;
```

#### 3.2.2 查询消息列表（含过期过滤）

```sql
SELECT n.*, un.read_status, un.read_time, un.handle_status, un.handle_time
FROM bs_notice n
JOIN bs_notice_user un ON n.id = un.notice_id
WHERE un.user_id = '当前用户ID'
  AND un.is_deleted = 0
  AND (n.expire_time IS NULL OR n.expire_time > NOW())
ORDER BY n.send_time DESC
LIMIT 20 OFFSET 0;
```

#### 3.2.3 查询待办（未处理）

```sql
SELECT n.*, un.*
FROM bs_notice n
JOIN bs_notice_user un ON n.id = un.notice_id
WHERE un.user_id = '当前用户ID'
  AND un.is_deleted = 0
  AND n.msg_type = 4
  AND un.handle_status = 0
  AND (n.expire_time IS NULL OR n.expire_time > NOW())
ORDER BY n.send_time DESC;
```

## 5 `rec_table` 业务表标识（标准化）

> 定义所有支持关联的业务表标识，便于统一管理和查询。

| rec_table 标识 | 对应表名 | 说明 |
|---------------|---------|------|
| `booking_order` | `dwd_booking_order` | 预订订单主表 |
| `booking_order_detail` | `dwd_booking_order_detail` | 预订订单明细表 |
| `vehicle_ad_position` | `dwd_vehicle_ad_position` | 车位广告表 |
| `on_air_order` | `dwd_on_air_order` | 上刊订单主表 |

## 9 小结

- **核心表：2 张**（`bs_notice` + `bs_notice_user`）
- `send_type` 用来定义"如何解析接收人范围"，复杂接收人场景统一推荐 `send_type=5` + `extra_data` 组合
- 模板表当前可不做：用静态模板常量集中管理即可
- **全部业务场景已覆盖**：预订、上刊、下刊、AI审核、调线审核、系统广播
