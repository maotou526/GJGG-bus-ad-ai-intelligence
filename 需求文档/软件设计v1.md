## 0 核心角色与权责定义

本系统支持**自营广告**和**代理商运营广告**双模式，涉及多个核心角色协同工作。

### 0.1 角色体系

#### 0.1.1 广告公司媒体部
**定位**：系统核心管理者，全业务流程管控

**核心权责**：
- 资源统筹管理（线路、车辆、媒体资源配置）
- **自营广告**：从预订、审批、上下刊执行到监测的全流程管理
- **代理商广告**：审批管控（订单审批、画面合规审查）
- 数据监控管理与报表查看
- 施工团队管理

**细分子角色**：
- **媒体部业务专员**：负责自营广告订单处理、资源调配
- **媒体部施工团队**：负责自营广告的现场上下刊施工
- **媒体部审查员**：负责自营广告的画面内容审查
- **媒体部合规审查员**：负责代理商广告的合规性审查
- **媒体部施工管理员**：负责上下刊工单验收确认

#### 0.1.2 广告代理商
**定位**：代理商运营广告的前端执行者

**核心权责**：
- 客户开发与维护
- 订单提交（需经媒体部审批）
- 广告画面设计与提报
- **自主提交上下刊执行**（代理商自行安排施工）
- 订单流程追踪

**操作权限**：
- 仅能查看和操作被授权的资源范围
- 订单需经媒体部审批
- 上刊画面需经媒体部合规审查

#### 0.1.3 营运分公司广告专员
**定位**：广告执行与车辆调度的协同者

**核心权责**：
- **订单审批确认节点**：确认车辆/站点调度可行性（自营+代理商订单都需要）
- **刊间监测**：每月一次完成全量广告（自营+代理商）的监测工作
- 反馈投放异常问题（画面破损、位置偏移等）
- 上下刊工单的调度协调确认
- 调度冲突预警与应急处理

#### 0.1.4 广告公司管理层
**定位**：企业经营决策者

**核心权责**：
- 业务数据复盘与分析
- 运营策略制定
- 成本效益分析
- 查看多维度数据统计报表（自营/代理商营收对比、资源利用率等）

**操作权限**：
- 仅查看权限，不参与实际业务操作

### 0.2 双模式业务流程差异

#### 0.2.1 自营广告流程

| 环节 | 负责角色 | 说明 |
|------|---------|------|
| 订单预订 | 媒体部业务专员 | 发起订单 |
| 订单审批 | 媒体部（多节点）+ 营运广告专员 | 资源、预算、调度可行性审批 |
| 画面审查 | 媒体部审查员 | AI预审 + 人工综合审查 |
| 上刊执行 | 媒体部施工团队 | 媒体部安排施工 |
| 施工验收 | 媒体部施工管理员 | 验收确认 |
| 刊间监测 | 营运广告专员 | 每月监测 |
| 下刊执行 | 媒体部施工团队 | 媒体部安排施工 |

#### 0.2.2 代理商运营广告流程

| 环节 | 负责角色 | 说明 |
|------|---------|------|
| 订单预订 | 代理商 | 发起订单 |
| 订单审批 | 媒体部（资源审核）+ 营运广告专员 | 仅审核资源可用性与合规性 + 调度可行性 |
| 画面审查 | 媒体部合规审查员 | AI预审 + 合规性复核 |
| 上刊执行 | **代理商自主执行** | 代理商安排自己的施工队伍 |
| 施工验收 | 媒体部施工管理员 | 验收确认 |
| 刊间监测 | 营运广告专员 | 每月监测 |
| 下刊执行 | **代理商自主执行** | 代理商安排自己的施工队伍 |

### 0.3 关键差异点总结

| 对比项 | 自营广告 | 代理商广告 |
|-------|---------|-----------|
| **订单发起** | 媒体部业务专员 | 代理商 |
| **审批流程** | 多节点全流程审批 | 简化审批（仅资源和合规） |
| **画面审查** | 综合审查（创意、品牌、信息） | 合规审查（法律、证明文件） |
| **施工执行** | 媒体部施工团队 | 代理商自主施工 |
| **管控粒度** | 全流程深度管控 | 审批+验收管控 |

### 1.2 车辆管理

**功能目标**：建立车辆专属档案（**自编号、车牌号、车型、所属线路**），支持车辆与线路的关联/解绑，实时同步车辆运营状态（报废/营运）。

**业务逻辑**：
- 车辆必须关联线路才能作为广告资源使用
- 车辆运营状态变化（如报废、检修）需实时同步并影响关联的广告资源状态
- 支持车辆在不同线路间调配（解绑/重新关联）
- 一辆车可以有多个广告资源位，每个资源位对应不同的媒体类型（通过广告资源位表关联）

**数据表设计**：

### 1.3 媒体类型管理

**功能目标**：明确划分媒体类型（车身、站点灯箱等），支持组合媒体类型（如"大三侧"="车尾+左侧+右侧"，"全车身"="车头+车尾+左侧+右侧"），每种类型建立标准属性（规格参数、制作要求、刊例价基准）。

**业务逻辑**：
- 媒体类型分为**基础类型**和**组合类型**
- **基础类型**：不可再分的最小单元，如"车头"、"车尾"、"左侧"、"右侧"、"普通灯箱"等
- **组合类型**：由多个基础类型组成，如：

- 前端用户只选择组合类型（如"大三侧"、"全车身"），系统自动关联其包含的所有基础类型
- 每个基础类型对应实际的广告位物理位置

### 1.4 广告资源位管理

**功能目标**：记录每辆车的每个广告位（基础媒体类型）的状态，支持上刊时的冲突检测和资源占用管理。

**业务逻辑**：
- 每辆车的每个基础媒体类型（车头、车尾、左侧、右侧等）对应一个广告资源位
- 资源位记录当前状态：空闲、预订、在刊、维修等
- 预订组合类型时，系统自动检查所有包含的基础类型资源位是否可用
- 只有所有基础类型资源位都可用，才能预订成功
- 上刊/下刊操作会自动更新关联的所有基础资源位状态

**业务约束**：
- 同一车辆 + 同一广告位 可以有多条记录（不同时间段的预订）
- **时间段冲突检测**：同一 `(vehicle_id, base_media_type_id)` 的有效记录（状态为2或3），`scheduled_start_date` 至 `scheduled_end_date` 时间段不能重叠
- 预订时创建记录，状态为"预订"；上刊完成后更新为"在刊"；下刊完成后更新为"已下刊"，记录保留作为历史
- `resource_code` 保持唯一，格式建议：`V{车辆ID}-{媒体类型ID}-{YYYYMMDD}`

**状态流转规则**：
```
预订(2)：创建预订单，锁定资源
预订(2) → 在刊(3)：上刊工单完成，填写 on_air_date
在刊(3) → 已下刊(6)：下刊工单完成，填写 off_air_date，记录保留作为历史
预订(2) → 不可用(5)：车辆维修/线路调整，填写 unavailable_* 字段
在刊(3) → 不可用(5)：车辆维修/线路调整，填写 unavailable_* 字段
不可用(5) → 原状态：恢复可用，清空 unavailable_* 字段
```

**说明**：
- 状态1（空闲）不再使用，因为每条记录都对应一个具体的预订/投放周期
- 查询"可用资源"时，通过检查该车位在指定时间段内是否有状态为2或3的记录来判断

### 1.5 线路调线审核

**功能目标**：当车辆因运营调整切换线路时，系统自动触发调线审核流程，通知负责人处理受影响的广告资源，支持"忽略"或"重做"两种处理方式。

**业务逻辑**：
- 车辆切换线路时，自动触发调线审核，生成审核主记录
- 系统自动检测该车辆当前所有"在刊"或"已预订"状态的广告资源位
- 为每个受影响的资源位生成审核明细记录，待负责人处理
- **处理方式**：
  - **忽略**：不做业务变更，仅记录日志，适用于临时调整

   - 自动创建3条明细记录

2. **负责人处理**：
   ```
   明细1：车头 - 客户A广告 - 选择"忽略"
   ```

   - 对于"重做"：
     - 为原车辆（车辆100）生成下刊工单
     - 为替换车辆（车辆200）生成上刊工单
     - 更新资源位状态
     - 记录工单ID到明细表

**业务约束**：
- 一个调线审核主记录可以有多个明细记录
- 只有所有明细都处理完成后，主表状态才能更新为"已完成"
- 同一订单的多个资源位应该选择相同的处理方式和替换车辆

### 2.3 广告预订

**功能目标**：实现订单从发起、审批、生成到变更的全生命周期线上化管理，支持自营和代理商双模式差异化流程。

**业务逻辑**：
- **双模式订单**：通过通用字段 `agent_id` 区分（NULL=自营，有值=代理商）
- **车身广告 vs 车位广告**：
  - **车身广告**：预订单明细层面，只记录线路、媒体类型、数量（不指定具体车辆）
  - **车位广告**：执行层面，系统自动分配具体车辆+资源位（提交审批时创建）
- **资源校验**：提交时校验资源档期与车辆运营状态，规避排期冲突
- **最优分配算法**：提交审批时，系统根据算法自动分配最优的车辆资源位组合
- **差异化审批**：
  - 自营订单：多节点审核（资源、预算、策略）+ 营运专员确认
  - 代理商订单：简化审核（资源、合规）+ 营运专员确认
- **订单变更**：
  - 基于原订单复制生成新版本订单（booking_type=3）
  - 用户在新订单上修改投放细节后，发起全新的审批流程
  - 原订单 `enabled_mark=0`（停用），作为历史保留
  - 新订单通过 `original_booking_id` 关联原订单
  - 新订单审批通过后，替代原订单成为执行依据
- **状态流转**：草稿 → 待审批 → 审批中 → 已通过 → 已完成
- **执行管理**：上刊、下刊状态由工单表管理，订单只管理预订状态

**数据表设计**：

#### 2.3.5 预订单审批流程

*说明：预订单从提交到通过的完整审批流程，基于 `node_workflow` 工作流引擎实现。*

**流程节点**：
```
提交 → 媒体部初审 → 营运公司审核（会签） → 媒体部复审 → 通过/驳回
```

**一、提交阶段**

代理商/自营提交预订单时，系统自动执行以下操作：

1. **生成车位广告**：根据预订单明细表（车身广告）自动分配具体车辆，生成 `VehicleAdPositionModel` 记录
2. **锁定资源**：同步创建 `VehicleAdResourceModel` 记录（排期数据），状态设为"预订"
3. **更新状态**：预订单状态变为"待媒体部初审"

**资源分配校验规则**：

- **代理商授权车辆数校验**：校验 `AgentResourceAuthModel.auth_ad_bus_count`，如果预订数量超过授权车辆数，在表单中显示警告提醒（不阻止提交，由媒体部最终决定）

**资源锁定模式**（通过系统配置切换）：

| 模式 | 配置项 | 说明 |
|:---|:---|:---|
| **整车锁定（默认）** | `RESOURCE_LOCK_MODE = 'vehicle'` | 一辆车被预订后，在投放周期内整车锁定，不能再做任何其他广告。即同一时间段内，一辆车只能被一个订单占用。 |
| **资源位锁定** | `RESOURCE_LOCK_MODE = 'position'` | 只锁定具体的资源位，同一辆车可以被多个订单共用（前提是资源位不冲突）。例如：车头做A广告，车尾可以做B广告。 |

**默认模式（整车锁定）校验逻辑**：
```
1. 检查目标车辆在投放周期内是否已被其他订单占用
2. 已占用 → 跳过该车辆，选择下一辆
3. 未占用 → 锁定整车，标记为"已预订"
```

**资源位锁定模式校验逻辑**：
```
1. 检查目标车辆的具体资源位（media_json.resource_ids）在投放周期内是否被占用
2. 任一资源位被占用 → 跳过该车辆
3. 所有资源位均空闲 → 锁定对应资源位
```

> **设计说明**：组合媒体类型（如大三侧、全车身）和单一媒体类型（如车头、车尾）的设计是为了适应不同业务场景。默认采用整车锁定模式更简单直观；资源位锁定模式提供更精细的资源管理能力，可通过配置开启。

**二、媒体部初审**

媒体部收到预订单后，可执行以下操作：

| 操作 | 说明 |
|:---|:---|
| **查看** | 查看所有车位广告及资源分配情况 |
| **新增** | 新增车位广告（需校验资源可用性） |
| **删除** | 删除车位广告（同步释放资源） |
| **修改** | 修改车位广告（换车、换媒体类型等） |
| **通过** | 同意后流转到营运公司审核 |
| **驳回** | 拒绝订单，订单状态变为"已驳回"，释放所有资源 |

**通过操作**：
- 根据车位广告涉及的营运公司，通过工作流引擎创建会签任务
- 预订单状态变为"待营运公司审核"

**驳回操作**：
- 删除所有 `VehicleAdPositionModel` 记录
- 释放所有 `VehicleAdResourceModel` 记录（删除或状态改为空闲）
- 记录驳回原因、驳回节点、驳回人、驳回时间

**三、营运公司审核（会签模式）**

媒体部初审通过后，系统根据车位广告涉及的营运公司自动分发任务：
- 涉及几家营运公司，就发给几家广告专员
- 采用**会签模式**：所有营运公司都完成审核后，才流转到下一节点

**营运公司广告专员可执行的操作**：

| 操作 | 说明 |
|:---|:---|
| **确认** | 打勾确认车位广告，`confirm_status` 设为"已确认" |
| **换车** | 只能更换同线路的其他车辆（选车），需校验新车辆资源可用性，不能更改媒体类型 |
| **剔除** | 剔除车位广告，`confirm_status` 设为"已剔除"，必须填写 `exclude_reason` |

**操作范围限制**：
- 营运公司广告专员只能查看和操作属于自己公司的车位广告
- 只能调整车辆（换车），不能修改线路、媒体类型等其他信息

**完成条件**：
- 该公司所有车位广告都已处理（确认或剔除）
- 所有营运公司都完成审核后，自动流转到媒体部复审

**四、媒体部复审**

营运公司审核完成后，媒体部进行最终复审：
- 操作权限与媒体部初审相同（增删改查车位广告）
- 可以查看营运公司的确认/剔除情况及原因
- 通过后订单状态变为"已通过"，订单正式生效
- 驳回后订单状态变为"已驳回"，释放所有资源

**五、重新发起（已驳回订单）**

被驳回的订单可以重新发起：

1. **复制订单**：生成新订单（新的 `booking_no`），`booking_type` 设为"重新发起"，`original_booking_id` 指向被驳回的原订单
2. **复制明细**：复制原订单的预订单明细
3. **智能分配车位**：生成车位广告时，优先沿用原订单的车位分配（相同线路+媒体类型+车辆），只有当原车辆资源已被占用时才重新分配
4. **保留调整记录**：尽可能保留媒体部或营运公司之前调整过的资源分配

**沿用资源的逻辑**：
```
1. 查询原订单的车位广告记录
2. 对于每条明细，检查原车辆在新时间段是否可用
3. 可用 → 直接沿用原车辆
4. 不可用 → 按最优算法重新分配
```

**六、与工作流引擎集成**

预订单审批流程通过 `node_workflow` 工作流引擎实现：

| 工作流概念 | 预订单对应 |
|:---|:---|
| 流程模板 | 预订单审批流程模板（scheme_code） |
| 流程实例 | 每个预订单对应一个流程实例 |
| 任务节点 | 媒体部初审、营运公司审核、媒体部复审 |
| 会签节点 | 营运公司审核（多家公司并行会签） |
| IOC 方法 | 获取营运公司审核人、流转时更新订单状态等 |

**需要实现的 IOC 方法**：
- `GetCompanyAuditors`：根据车位广告获取涉及的营运公司广告专员
- `OnBookingApproved`：订单审批通过时的业务处理
- `OnBookingRejected`：订单驳回时释放资源

## 3 上下刊执行模块

### 3.1 上刊管理

**功能目标**：在计划上刊日期前5个工作日自动生成上刊工单，管理广告画面材料提报、审批审核、施工团队、现场执行全流程。

**业务逻辑**：
- **自动触发**：系统在预订单的 `start_date` 前5个工作日自动生成上刊申请
- **材料管理**：上传广告画面文件、合规证明文件、施工方案等（同一预订单产生的上刊申请对应的材料应该是一样的，材料仅用于审核，不关联具体车位）
- **审批流程**：通过统一的审批流引擎（AI预审 → 人工审查 → 营运确认）
- **施工团队**：关联施工负责人和团队成员
- **现场验收**：上传施工照片，媒体部管理员确认
- **到期未下刊检测**：
  - 施工人员在小程序中执行上刊操作时，系统自动检测目标车辆资源位是否存在到期未下刊的广告
  - 检测规则：查询 `VehicleAdResourceModel`，如果 `resource_status = 3 (在刊)` 且关联的预订单 `end_date < 当前日期`，则判定为到期未下刊
  - 检测到到期未下刊时，系统自动跳转到下刊工单，要求施工人员先完成下刊操作
  - 下刊完成后，才允许继续执行上刊操作
- **上刊前冲突检测**：
  - 检查目标车辆资源位的 `resource_status`，如果为 `3 (在刊)` 且未到期，则拒绝上刊
  - 检查是否有时间段重叠的已上刊记录（查询 `VehicleAdPositionModel`）
- **【待设计】扫码签到功能**：
  - 建设需求文档3.1.7提到"施工人员抵达现场扫码签到"
  - 当前设计暂不包含实际的扫码签到记录表
  - `OnAirWorkerModel` 的 `actual_entry_time/exit_time` 可手动填写进离场时间
  - 后续可考虑新增 `CheckInModel` 表记录实际签到记录

- 一个上刊订单包含多个明细
- 关联预订单的车位广告表（`VehicleAdPositionModel`）

- `media_json` 结构与 `VehicleAdPositionModel.media_json` 相同，存储占用的基础资源位详情
- **实际上刊车辆可能与预订车辆不同**（如调车、维修等原因），这是正常的业务场景

- **上刊订单完成条件**：只有当所有关联的明细的 `execution_status = 3 (已完成)` 时，上刊订单的 `order_status` 才能更新为 `6 (已完成)`

  - 如果施工人员填写的 `act_vehicle_id` 与 `plan_vehicle_id` 不一致，提交后进入人工审核流程。
  - **媒体部处理决策**：
    - **方案A（认可变更）**：媒体部人员需**手动在系统中调整车辆分配**（修改 `VehicleAdPositionModel`），系统将自动联动更新实时车位资源表 (`VehicleAdResourceModel`) 的状态，确保库存准确性。
    - **方案B（拒绝变更）**：审核驳回，要求施工人员重新去正确的车辆上刊，或者重新提交证据。

- **组合媒体类型保留**：
  - `composite_media_type_id` 保留预订时的业务语义，知道用户原本预订的是组合类型（如"大三侧"）还是单独预订的基础类型
  - 如果用户单独预订基础类型（如只订"车尾"），则 `composite_media_type_id` 为 NULL
  - 便于后续统计分析（如"大三侧"类型的订单量、上刊率等）

### 3.2 审查标准能力（AI智能审核）

**功能目标**：基于阿里百炼智能体实现广告画面的自动化合规审核，检测违规内容、标注风险点，提升审核效率，为人工复核提供参考依据。

**业务场景**：

系统支持**两种AI审核场景**：

1. **关联订单审核**（订单流程内）
   - 用户在提交上刊申请时，上传广告画面及合规证明材料
   - 系统自动触发AI审核，材料关联到 `OnAirMaterialModel` 和 `OnAirOrderModel`
   - 审核结果作为订单审批的参考依据

2. **独立审核**（独立功能）
   - 用户直接上传广告画面文件，不关联任何订单
   - 典型用途：
     - 设计师设计完成后的预审
     - 客户提前检测画面合规性
     - 临时性的画面审核需求
   - 审核结果仅供参考，不影响订单流程

两种场景均调用**阿里百炼智能体**进行检测（违禁词、绝对化用语、画面质量等），记录审核结果供人工参考。

**业务逻辑**：

- **触发时机**：
  - **关联订单审核**：材料上传到 `OnAirMaterialModel` 后立即触发异步AI审核任务
  - **独立审核**：用户在独立审核页面上传文件后立即触发

- **审核范围**：
  - 关联订单审核：所有 `material_category=1 (广告画面)` 的材料必须经过AI审核
  - 独立审核：用户自主上传任何图片文件

- **审核流程**：
  - 关联订单：材料上传 → AI自动审核 → 记录结果 → 更新材料状态 → 流转人工复核
  - 独立审核：文件上传 → AI自动审核 → 记录结果 → 展示审核报告

- **判定规则**：
  - AI通过 + 无风险 → 自动流转人工复核（关联订单）或展示通过结果（独立审核）
  - AI疑似违规 → 标注风险点，等待人工审核
  - AI明确违规 + 高置信度 → 自动驳回或强制人工审核

- **超时处理**：AI审核超过60秒未响应，标记为"审核失败"，自动转人工审核流程

- **反馈学习**：人工审核员对AI结果的反馈用于模型持续优化

**技术实现要点**：


1. **异步审核机制**（Celery任务）
   
   **关联订单审核**：
   - 材料上传到 `OnAirMaterialModel` 后立即入队
   - 更新 `audit_status = 11 (AI审核中)`
   - 调用阿里百炼API，传入文件URL、材料类型
   - 解析返回结果，创建 `AIAuditLogModel` 记录（`audit_source=1`）
   - 更新 `audit_status` (10->20/30/40) 和 `latest_ai_audit_id`
   - 发送通知给审核员
   
   **独立审核**：
   - 用户上传文件后直接存储到临时目录或MinIO
   - 调用阿里百炼API进行审核
   - 创建 `AIAuditLogModel` 记录（`audit_source=2`，`material_id=NULL`，`order_id=NULL`）
   - 实时返回审核结果给前端展示
   - 不更新任何订单或材料状态

2. **API调用封装**
   - 统一封装阿里百炼API调用逻辑
   - 处理超时（60秒）、重试（最多3次）、异常
   - 记录完整的请求/响应日志到 `raw_response` 字段

3. **风险判定规则**
   ```python
   # 伪代码示例
   def auto_determine_status(ai_result, audit_source):
       if audit_source == 1:  # 关联订单审核
           if ai_result['conclusion'] == 'pass' and ai_result['risk_level'] == 1:
               return 30  # 已通过 (低风险自动通过)
           elif ai_result['conclusion'] == 'fail' and ai_result['confidence_score'] >= 90:
               return 40  # 已驳回 (高置信度违规)
           else:
               return 20  # 待人工复核
       else:  # 独立审核，不更新状态
           return None
   ```

4. **审批流程集成**
   
   **关联订单审核流程**：
   ```
   上刊申请提交
     ↓
   材料上传 (OnAirMaterialModel)
     ↓
   触发AI自动审核 (异步) ← 新增环节
     ↓
   人工复核 (参考AI结果)
     ↓
   营运调度确认
     ↓
   审批完成
   ```
   
   **独立审核流程**：
   ```
   独立审核页面
     ↓
   上传文件
     ↓
   触发AI审核 (异步)
     ↓
   展示审核报告
     ↓
   用户查看结果（不影响订单）
   ```

**关键业务规则**：

1. **强制AI审核**：
   - 关联订单审核：所有广告画面（`material_category=1`）必须经过AI审核才能流转人工复核
   - 独立审核：用户自愿使用，无强制要求

2. **审核超时处理**：超过60秒未响应，标记为"审核失败"
   - 关联订单：自动转人工审核
   - 独立审核：返回失败提示给用户

3. **高风险自动拦截**：
   - 关联订单：`risk_level >= 4` 且 `confidence_score >= 90` 时自动驳回
   - 独立审核：仅展示高风险提示，不做拦截

4. **审核记录保留**：所有AI审核记录（包括独立审核）永久保留，用于审计和模型优化

5. **人工反馈机制**：
   - 关联订单：审核员必须对AI结果给出反馈
   - 独立审核：可选反馈，用于持续优化


**后续扩展方向**：

1. **合规知识库**：建立本地化的合规规则库，定期同步最新法规条款
2. **智能学习**：基于人工反馈优化AI判定规则，定期分析误判率和漏检率
3. **批量审核**：支持同一订单多个文件批量审核，汇总生成综合报告
4. **可视化标注**：在前端展示违规位置高亮，支持审核员在线标注修改建议

### 3.3 下刊管理

**功能目标**：实现广告下刊的全流程数字化管理，支持到期自动触发和异常手动触发，通过工单系统指派施工团队，利用移动端进行现场拆除存证，确保车辆广告位恢复原状。

**业务逻辑**：

- **触发机制**：
  - **自动触发**：系统定期扫描 `BookingOrderModel`，在 `end_date` 前5个工作日自动生成下刊工单（`off_reason=1`）。
  - **手动触发**：
    - **提前终止**：销售/管理人员手动发起，需关联客户终止协议。
    - **提前终止**：销售/管理人员手动发起，需关联客户终止协议。
    - **线路调整**：因线路调线审核通过，自动触发旧资源的下刊。
    - **破损重做**：**不直接触发下刊**，而是通过“**新预订**（变更订单）”流程，生成新的上刊/下刊工单闭环处理。

- **状态流转**：
  - 草稿 → 待审批（仅异常下刊需要） → 施工中 → 已完成
  - **正常到期下刊无需审批**，系统生成后直接分发给施工团队。

- **施工执行**：
  - **进场登记**：复用 `EntryRegModel`（`task_type=2`）。
  - **现场存证**：强制要求上传“下刊前”、“下刊中”、“下刊后（清洁）”三组照片。
  - **资源释放**：下刊工单完成后，自动更新 `VehicleAdResourceModel` 状态为“空闲”，并更新 `VehicleAdPositionModel` 的 `actual_off_date`。
